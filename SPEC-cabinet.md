# Спека: личный кабинет ученика и панель наставника (ветка `china`, блок C)

Решения владельца от 07.09.2026: вход по email (magic link); организация с несколькими
наставниками; наставническая часть — целиком; имя ученика не спрашиваем (необязательный ник
в профиле); наставник видит всё, что видит ученик, плюс последний визит и ответы онбординга
(ученику об этом сказано явно); хостинг — **второй** GitHub Pages сайт; удаление аккаунта — с
подтверждением по почте; задачи наставника ученик только отмечает выполненными, свои — может
удалять; **функции «отвязаться от наставника» у ученика нет** — снять ученика может наставник.

**Что это меняет в продукте.** Витрина остаётся бесплатной и работает без аккаунта, как сейчас
(каталог + план в браузере). Аккаунт — надстройка: план перестаёт жить в одном браузере, и
появляется связь с наставником. Кабинет — то, что продаётся организациям-консультантам.

**Инварианты (поверх инвариантов витрины):**
- Минимум ПДн: при регистрации — только email и согласие; ник необязателен; **никаких файлов
  и ссылок на файлы** — документы только как статусы «готов / не готов».
- Отдельный проект Supabase для приложения; конвейер до ученических данных не дотягивается.
- Единственный охранник — RLS. Публичный `anon`-ключ в сборке — норма; каждая политика покрыта
  тестом против реальной базы с двумя пользователями.
- Ученик видит ровно то, что видит наставник, и наоборот: никаких скрытых полей ни у кого.
- Каталог остаётся статическим `china.json`; кабинет ссылается на вузы по `University.id` (slug).
- Ни строчки логики фактов не меняется: `display` печатается как есть, провенанс — как есть.

## 0. Что нужно от владельца до реализации

1. **Проект Supabase** (новый, не конвейерный). В `app/.env.local` (gitignored):
   `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` — для приложения; `SUPABASE_DB_URL` (Session
   Pooler, порт 5432) — только для миграций и RLS-тестов с ноутбука, в сборку не попадает.
   Auth → URL Configuration: Site URL = адрес второго Pages-сайта; Redirect URLs =
   `http://localhost:5190/**` и `<pages-url>/**`. Провайдер Email включён (по умолчанию).
2. **Пустой репозиторий GitHub** под второй Pages-сайт (дефолт имени: `abitura-china`). После
   первого пуша ветки `gh-pages` — Settings → Pages → Source: branch `gh-pages`, root.
3. **Данные организации Zhuiqiu**: название, Телеграм (`zhuiqiu_yu`), email наставников — если
   пока нет, организация создаётся с инвайт-кодом, наставники добавляются позже скриптом.
   Аккаунт владельца (email из настроек) заводится наставником-администратором для проверки.

Без п.1 ночью пишется весь код, SQL и тесты чистой логики; RLS-тесты и миграции применяются,
как только появятся ключи. Без п.2 деплой откладывается, кабинет проверяется локально.

## 1. Модель данных (Postgres в Supabase, схема `public`)

```sql
-- профиль = 1:1 к auth.users; создаётся триггером при регистрации
profiles (
  user_id uuid pk references auth.users on delete cascade,
  nick text,                             -- необязательный, ≤ 40 символов
  onboarding jsonb,                      -- ChinaProfile из витрины (степень, направление, язык, HSK/IELTS, бюджет, год)
  consent_at timestamptz not null,       -- галочка политики при регистрации
  last_seen_at timestamptz,              -- обновляется клиентом не чаще раза в час
  created_at timestamptz default now()
)

organizations (
  id uuid pk, slug text unique,          -- 'zhuiqiu'
  name text, tagline text, telegram text, -- бренд кабинета ученика (то, что было в partners.ts)
  invite_code text unique,               -- 'ZHUIQIU-7F3K' — перевыпускается
  created_at timestamptz
)

org_members (org_id, user_id, role text check (role in ('admin','mentor')), added_at, pk (org_id, user_id))

mentorships (
  student_id uuid references profiles on delete cascade,
  org_id uuid references organizations,
  status text check (status in ('active','removed')) default 'active',
  joined_at timestamptz, removed_at timestamptz, removed_by uuid,
  pk (student_id, org_id)
)
-- инвариант: у ученика не больше ОДНОЙ active-организации (partial unique index)

plan_items (
  student_id, university_id text,        -- slug из china.json
  status text check (status in ('considering','preparing','applied','answered')) default 'considering',
  note text,                             -- заметка ученика
  added_at, updated_at, pk (student_id, university_id)
)

plan_docs (student_id, university_id, doc_id text, done bool, done_at, pk (student_id, university_id, doc_id))

tasks (
  id uuid pk, student_id uuid, org_id uuid null,   -- org_id null = задача ученика себе
  author_id uuid,                         -- кто создал
  university_id text null, title text (≤ 140), details text null,
  due_on date null, done_at timestamptz null,
  created_at, updated_at
)

mentor_notes (
  org_id, student_id, university_id text,
  body text (≤ 2000), author_id, updated_at,
  pk (org_id, student_id, university_id)
)
```

Триггеры: `handle_new_user()` → строка `profiles`; `set_updated_at()`. Функции (SECURITY DEFINER,
с проверками внутри): `join_org(code)` — привязка текущего пользователя по инвайт-коду (отказ,
если уже есть активная организация); `delete_own_account()` — удаляет `auth.users` текущего
пользователя (каскад уносит всё его); `org_remove_student(org, student)` — только для члена
организации, ставит `removed`. Ничего не удаляется, кроме аккаунта по воле владельца аккаунта.

## 2. RLS — и тест на каждую строку таблицы

| Таблица | Читает | Пишет |
|---|---|---|
| `profiles` | сам; члены его active-организации | сам (`nick`, `onboarding`, `last_seen_at`) |
| `organizations` | члены; **ученик своей active-организации** (для бренда) | admin организации |
| `org_members` | члены той же организации | admin |
| `mentorships` | ученик — свои; члены — своей организации | insert — только через `join_org`; `removed` — через `org_remove_student` |
| `plan_items`, `plan_docs` | ученик; члены его active-организации | **только ученик** |
| `tasks` | ученик; члены организации | ученик: insert со своим `student_id` и `org_id null`; update `done_at` любой своей задачи; delete — только `org_id is null`. Член организации: insert/update/delete задач с `org_id` = своя, `student_id` — её ученик |
| `mentor_notes` | ученик (своей организации); члены | только члены своей организации |

Тесты (`app/rls/rls.test.ts`, vitest, запускаются с `SUPABASE_DB_URL` + двумя тестовыми
пользователями, создаваемыми через admin API из service-role в тесте): ученик А не видит план
ученика Б; наставник организации X не видит ученика организации Y; ученик не может изменить
`mentor_notes`; ученик не может удалить задачу наставника, но может отметить выполненной;
`join_org` с чужим кодом второй раз — отказ; после `delete_own_account` строк нет. Без ключей
тесты пропускаются с явным сообщением, не падают.

## 3. Вход и сессия (`app/src/auth/`)

- `supabase.ts` — клиент из `import.meta.env.VITE_SUPABASE_*`; при отсутствии переменных
  кабинет выключен (`FEATURES.accounts=false`), витрина работает как раньше — без единого
  запроса наружу.
- `AuthGate` / `useSession()`; экран «Войти»: поле email + галочка согласия (ссылка на
  политику) → `signInWithOtp({ email, emailRedirectTo })` → «Проверьте почту». Ошибки —
  по-русски. Кнопка «Войти» — в сайдбаре и в «Моём плане» («сохранить план в аккаунте»).
- Возврат по magic link: `detectSessionInUrl`, хэш очищается. Если в `localStorage` лежит
  план (`admitica.cn.plan`) и в аккаунте пусто — предложение **перенести** одной кнопкой
  (`plan_items` + `plan_docs` + профиль); локальная копия после переноса помечается перенесённой,
  не удаляется.
- Инвайт: `?join=CODE` → после входа `join_org(code)` → тост «Ты подключён к Zhuiqiu» →
  бренд организации применяется. Без аккаунта ссылка ведёт на вход с сохранённым кодом.
- Выход — кнопка в профиле.

## 4. Кабинет ученика — что меняется на экранах

**«Мой план»** (`Plan.tsx`) читает/пишет через `lib/planStore.ts` — один интерфейс с двумя
реализациями: `localPlanStore` (как сейчас) и `remotePlanStore` (Supabase). Компоненты не знают,
какая под ними. Оптимистичные обновления; ошибка сети — тост, локальное состояние не теряется.

Новые блоки на «Моём плане»:
- **Задачи** (`TasksPanel`): лента «ближайшие 7 дней» вверху — задачи + дедлайны вузов + общие
  даты CSCA/CSC в одном списке (расширить `deadlineFeed`). Задача от наставника помечена именем
  организации, чекбокс «сделано», удалять нельзя; своя — можно. Форма «добавить задачу»: название,
  срок, вуз (необязательно).
- **Комментарий наставника** под карточкой вуза в плане — если есть.
- **Наставник** (`MentorCard`): название организации, кнопка в Телеграм, строка «Наставник видит
  твой план, документы, задачи и ответы онбординга». Если организации нет — поле «код
  приглашения» + кнопка.

**Профиль** (`Profile.tsx`, новая вкладка вместо «Настройки» для вошедших; настройки темы
остаются внутри): ник, ответы онбординга (редактируемые, тот же компонент, что в онбординге),
экспорт данных (JSON), **удалить аккаунт**: кнопка → письмо с magic link на
`?confirm=delete` → на возврате экран «Удалить аккаунт и все данные?» → `delete_own_account()`
→ выход, локальные ключи `admitica.cn.*` очищаются.

Витрина (`Find`, `Detail`) — без изменений, кроме «В мой план» через `planStore`.

## 5. Панель наставника (`app/src/mentor/`)

Показывается членам организации вместо ученического кабинета (переключатель, если человек и
ученик, и наставник — маловероятно, но не ломать).

- **Ученики** (`MentorStudents`): таблица — ник или «ученик #a1b2», вузов, ближайший дедлайн
  (из плана + задач), документы %, открытых задач, последний визит. Сортировка по ближайшему
  дедлайну; фильтр «горит на неделе». Кнопка «снять с сопровождения» (→ `removed`, с
  подтверждением; ученик видит, что наставника больше нет).
- **Карточка ученика** (`MentorStudent`): ровно ученический «Мой план» в режиме чтения (те же
  компоненты с пропом `readOnly`), профиль (ответы онбординга — с пометкой «ученик знает, что
  вы это видите»), задачи с формой добавления/правки/удаления, комментарий к каждому вузу.
- **Приглашение** (`MentorInvite`): ссылка `<site>/?join=CODE`, кнопка «скопировать»,
  «перевыпустить код» (старый перестаёт работать; уже привязанные не затрагиваются).
- **Организация** (`MentorSettings`, только admin): название, слоган, Телеграм, участники
  (список; добавление участника — по email, если у него уже есть аккаунт; иначе — сообщение,
  что ему нужно сначала войти).

Панель — в той же дизайн-системе, без новых токенов; на 375 таблица учеников превращается в
карточки.

## 6. Бренд из базы

`getPartner()` получает третий источник: организация ученика (после `?partner=` для гостей и
`VITE_PARTNER`). `partners.ts` остаётся как фолбэк для гостей и демо.

## 7. Деплой: второй Pages-сайт

- Скрипт `npm run deploy:china` в `app/package.json`: `vite build` → пуш содержимого `dist/` в
  ветку `gh-pages` репозитория владельца (`git subtree`/`gh-pages`-подобный пуш через SSH с
  этой машины). База `./` уже относительная — работает под `/<repo>/`.
- Переменные сборки: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_PARTNER` не задаётся
  (публичная сборка без бренда). Ключи читаются из `app/.env.local`; в git не попадают.
- Прод-сайт европейской Абитуры не трогается; `deploy.yml` в этом репозитории как был.

## 8. Тесты и приёмка

- vitest: `planStore` (обе реализации; удалённая — с мок-клиентом), `deadlineFeed` с задачами,
  `join`-парсер, редьюсеры задач, экспорт JSON; RLS-тесты (§2) при наличии ключей.
- `npm run build`, `npm run lint` — зелёные.
- Ручная приёмка на локальном сервере: регистрация → письмо → вход → перенос локального плана
  → инвайт-код → задача от наставника видна ученику → ученик отметил → наставник видит →
  комментарий к вузу → удаление аккаунта через письмо. В обеих темах, на 375.
- Скриншоты в `docs/screens/cabinet/`.
